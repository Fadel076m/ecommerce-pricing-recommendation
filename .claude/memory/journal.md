Jalon 5 (Forecasting) terminé le même jour, toujours en avance sur la roadmap (prévu vendredi 21/08). Scope : comparaison Baseline Moving Average / Prophet sur la demande quotidienne **agrégée** (Prophet ne gère qu'une série à la fois), + un modèle LightGBM **global** (panel produit×jour, `product_id` en feature catégorielle, 2961 produits retenus avec ≥30 jours d'historique) pour servir `/forecast/{product_id}` pour n'importe quel produit sans entraîner 4600 modèles (BDR-009). Split temporel strict (30 derniers jours en test), testé (`tests/test_forecasting.py`, pas de fuite du futur). Résultats loggés dans MLflow (expérience `forecasting`) : Prophet bat la baseline sur l'agrégé (MAE 8066 vs 10540, RMSE 15344 vs 16663) — critère de validation du jalon rempli. Le MAPE explose sur les trois modèles (314 327 % / 85 553 % / 296 %) car la demande quotidienne passe souvent proche de 0, exactement l'avertissement de la roadmap — MAE/RMSE retenus comme métriques de référence, documenté dans `docs/forecasting.md`. Accroc rencontré : MLflow plante sur console Windows (cp1252) à cause d'emojis imprimés sur stdout, même après un run réussi (LRN-008) — fix générique (`sys.stdout.reconfigure(encoding="utf-8")`) à réutiliser pour les Jalons 6/7. `.gitignore` durci pour `models/` (n'excluait que `*.pkl`/`*.joblib`, ratait le `.txt` du booster LightGBM). 23 tests Pytest passent au total.

Jalon 6 (Pricing) terminé le même jour. `src/pricing/` : elasticity.py (régression log-log par produit, éligibilité ≥20 obs/≥5 prix distincts/CV>5%, fallback assumé -1,5 documenté sinon, bornage [-10,0] après avoir constaté des élasticités positives en sortie brute), simulate.py (grille de 13 prix -30%/+30%, demande à élasticité constante, marge = (prix-cost_price)×demande, argmax), train.py (orchestration + MLflow, expérience `pricing`, résultats persistés dans `models/pricing_recommendations.parquet` pour l'API du Jalon 8). Audit préalable en SQL direct : seuls 1057/4631 produits ont assez de variation de prix pour une estimation crédible (confirmé ensuite par le code : 1057 estimés, 3574 sur fallback). Bug rencontré : un prix à 0 (article offert, valide selon data_quality.md) fait planter `np.polyfit` en `log(0)` (LRN-009) — filtré en amont. R² médian des produits estimés très faible (0,12), documenté sans détour dans `docs/pricing.md` avec toutes les réserves (77% du catalogue en fallback, uplift de marge simulé sur cost_price synthétique — jamais un gain réel). 11 tests Pytest dans `tests/test_pricing.py` (dont un qui vérifie le bornage sur bruit pur). 34 tests Pytest passent au total.
